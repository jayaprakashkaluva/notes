## 1. What Spark Actually Is

Spark is best read as **four layers stacked on one distributed execution kernel**:

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Language frontends: Scala/Java DSL, PySpark, SparkR, SQL, Connect     │
  ├──────────────────────────────────────────────────────────────────────┤
  │ Catalyst: parse → analyze → optimize → plan   (sql/api, sql/catalyst) │
  │ Tungsten: whole-stage codegen, UnsafeRow, vectorized readers          │
  ├──────────────────────────────────────────────────────────────────────┤
  │ Execution kernel: RDD + DAGScheduler + TaskScheduler + shuffle        │
  │                   BlockManager + MemoryManager           (core)       │
  ├──────────────────────────────────────────────────────────────────────┤
  │ Cluster substrate: YARN / Kubernetes / Standalone / local             │
  └──────────────────────────────────────────────────────────────────────┘
```

The critical architectural fact: **everything above the kernel compiles down to RDDs.**
A DataFrame query, a Structured Streaming micro-batch, an MLlib fit, a GraphX Pregel
iteration — all of them terminate in `SparkContext.runJob` on an RDD lineage. This is why
the DAGScheduler is the single most load-bearing class in the codebase, and why its
invariants (stage boundaries at shuffles, determinism, epoch-based failure fencing) leak
into the semantics of every layer above.

The second critical fact: **Spark's fault-tolerance model is recompute-from-lineage, not
replication.** A lost partition is regenerated by re-running its narrow-dependency chain
from the last materialized boundary. This makes shuffle output the de-facto checkpoint of
the system, and makes *determinism* of the RDD chain a correctness requirement rather than
a nicety (see `RDDOutputDeterministicLevel` and indeterminate-stage rollback in
[spark-core-internals.md](spark-core-internals.md#7-indeterminate-stages-and-rollback)).

Rough scale: `core` ≈ 300k lines of Scala/Java, `sql/catalyst` ≈ 440k. Catalyst being
larger than the kernel is the clearest signal of where the last decade of engineering
investment went.

### 2.1 The `sql/api` split

`sql/api` exists because Spark Connect needs a client that does *not* depend on Catalyst.
Types (`DataType`, `StructType`), `Column`, `Row`, encoders, and the `Dataset`/
`SparkSession` *interfaces* live in `sql/api`; the Catalyst-backed implementations live in
`sql/core`, and the proto-backed implementations live in `sql/connect/client/jvm`. This is
why the Connect client JAR is a few MB rather than a few hundred. `sql/connect/shims`
exists to stub out the handful of classes the client would otherwise pull in.

## 3. Process Architecture

```
              ┌───────────────────────── DRIVER JVM ─────────────────────────┐
              │  SparkContext                                                │
              │    ├─ SparkEnv (rpcEnv, serializer, blockManager, memory,    │
              │    │            shuffleManager, mapOutputTracker, metrics)   │
              │    ├─ DAGScheduler        (event loop thread)                │
              │    ├─ TaskSchedulerImpl   + SchedulerBackend                 │
              │    ├─ LiveListenerBus     (AsyncEventQueue x N)              │
              │    ├─ MapOutputTrackerMaster                                 │
              │    ├─ BlockManagerMasterEndpoint                             │
              │    ├─ ExecutorAllocationManager (dynamic allocation)         │
              │    ├─ ContextCleaner      (ReferenceQueue-driven GC)         │
              │    └─ HeartbeatReceiver                                      │
              └────────────────┬─────────────────────────────────────────────┘
                               │  Netty RPC (control) + Netty block transfer (data)
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
 ┌─── EXECUTOR JVM ───┐  ┌─── EXECUTOR JVM ───┐  ┌─── EXECUTOR JVM ───┐
 │ CoarseGrained-     │  │                    │  │                    │
 │   ExecutorBackend  │  │  (identical)       │  │  (identical)       │
 │ Executor           │  │                    │  │                    │
 │  ├ threadpool      │  │                    │  │                    │
 │  ├ TaskMemoryMgr   │  │                    │  │                    │
 │  ├ BlockManager    │  │                    │  │                    │
 │  └ python workers  │  │                    │  │                    │
 └────────────────────┘  └────────────────────┘  └────────────────────┘
                               │
                    (optional) External Shuffle Service — one per node,
                    survives executor death, serves shuffle blocks
```

**Driver** holds all scheduling state and is a single point of failure for the
application. **Executors** are long-lived, coarse-grained JVMs: they are allocated once
and run many tasks, which is the key difference from the per-task container model of
MapReduce and the reason Spark can cache data across stages at all.

### 3.1 Deploy modes

- **client mode** — driver runs in the submitting process; `SparkSubmit` (in `core/.../deploy`)
  loads the user's main class in-process. Good for interactive work, bad for flaky networks
  because the driver must stay reachable from every executor.
- **cluster mode** — driver runs inside a cluster-managed container (YARN
  `ApplicationMaster`, K8s driver pod). `SparkSubmit` becomes a thin launcher.
- **local[N] / local[*] / local-cluster** — `LocalSchedulerBackend` fakes offers against an
  in-process executor. `local-cluster` genuinely forks JVMs and is what most distributed
  tests use.

`ExternalClusterManager` (`core/.../scheduler/ExternalClusterManager.scala`) is the SPI: a
`ServiceLoader`-discovered factory that returns a `TaskScheduler` + `SchedulerBackend` pair
for a master URL. YARN and K8s are both implemented against it rather than being special-cased.

### 3.2 Executor lifecycle and resource profiles

`ResourceProfile` (`core/.../resource/`) generalizes "an executor" from a fixed
(cores, memory) pair to a bundle that includes custom resources (GPUs, FPGAs) with
discovery scripts and per-task fractional requests. Stages carry a resource profile ID;
`DAGScheduler.mergeResourceProfilesForStage` reconciles conflicting profiles when RDDs
with different profiles are pipelined into one stage. The `ExecutorAllocationManager`
tracks pending task demand *per profile* and asks the backend for that shape of executor.

## 4. The RPC Layer (`core/.../rpc/netty`)

Spark ships its own actor-ish RPC rather than using Akka (removed in 2.0). The design:

- `RpcEnv` — the environment; `NettyRpcEnv` is the only implementation.
- `RpcEndpoint` — a named message handler registered in the env. Has a lifecycle
  (`onStart`/`receive`/`receiveAndReply`/`onStop`) and **guaranteed sequential delivery**.
- `RpcEndpointRef` — a serializable handle. `send` is fire-and-forget; `ask` returns a
  `Future` with an `RpcTimeout` attached.
- `Dispatcher` + `Inbox` + `MessageLoop` — the concurrency core. Each endpoint has an
  `Inbox` (a message queue plus a `numActiveThreads` counter). The dispatcher's shared
  thread pool pulls from a queue of *endpoints that have work*, and the inbox guarantees
  only one thread processes a given endpoint at a time. This gives per-endpoint
  single-threading without one thread per endpoint.
- `Outbox` — per-remote-address send queue, so a slow peer can't block others.
- Two message loops exist: a shared one, and a dedicated one for endpoints that declare
  `IsolatedThreadSafeRpcEndpoint` (used where an endpoint must not be starved by others).

Endpoint names you will see in logs and stack traces: `CoarseGrainedScheduler`,
`BlockManagerMaster`, `BlockManagerEndpoint<N>`, `MapOutputTracker`, `HeartbeatReceiver`,
`OutputCommitCoordinator`, `StateStoreCoordinator`.

**Data does not travel over the RPC endpoints.** Bulk transfer (shuffle blocks, cached
block replication, broadcast chunks) goes through `BlockTransferService` /
`NettyBlockTransferService` on the `common/network-common` chunked-stream protocol, which
supports zero-copy `FileRegion` transfers and (for large blocks) streaming to disk instead
of into heap.

## 5. Job Submission: The End-to-End Path

Tracing `df.groupBy("k").count().collect()`:

1. **Frontend** — `Dataset.collect` calls `withAction`, which builds a `QueryExecution`.
2. **Catalyst** — parse (ANTLR) → analyze (catalog resolution, type coercion) → optimize
   (rule batches to fixed point) → plan (`SparkPlanner` strategies) → prepare
   (`EnsureRequirements` inserts exchanges, `CollapseCodegenStages` fuses operators).
   Detail: [spark-sql-catalyst-internals.md](spark-sql-catalyst-internals.md).
3. **Physical execution** — `SparkPlan.execute()` returns an `RDD[InternalRow]`. If AQE is
   on, the root is an `AdaptiveSparkPlanExec` that materializes query stages one at a time
   and re-plans between them.
4. **Kernel** — `SparkContext.runJob` → `DAGScheduler.submitJob` posts a `JobSubmitted`
   event onto the scheduler's `EventLoop`.
5. **Stage construction** — the DAGScheduler walks the RDD graph backwards, cutting at
   `ShuffleDependency` boundaries, creating `ShuffleMapStage`s and one `ResultStage`.
   Ancestor stages already materialized (tracked by `MapOutputTracker`) are skipped.
6. **Task dispatch** — `submitMissingTasks` serializes `(rdd, shuffleDep)` or `(rdd, func)`
   once, broadcasts it, builds one `Task` per missing partition with preferred locations,
   and hands a `TaskSet` to `TaskSchedulerImpl`.
7. **Offer matching** — `TaskSchedulerImpl.resourceOffers` receives `WorkerOffer`s from the
   backend, sorts task sets through the scheduling `Pool` (FIFO or FAIR), and lets each
   `TaskSetManager` pick tasks under delay-scheduling locality rules.
8. **Executor** — `Executor.launchTask` deserializes the `TaskDescription`, fetches
   dependencies (jars/files/archives) via `JobArtifactSet`, and runs `Task.run` on a
   thread from `Executor`'s pool with a fresh `TaskMemoryManager`.
9. **Result** — small results ride back in the `StatusUpdate` RPC; results over
   `spark.task.maxDirectResultSize` are stored in the BlockManager and fetched
   asynchronously by `TaskResultGetter`.
10. **Completion** — `DAGScheduler.handleTaskCompletion` registers map output or feeds the
    `JobWaiter`; the last partition completes the job.

The full walkthrough with failure branches is in
[spark-core-internals.md](spark-core-internals.md).

## 6. Event Bus, Status Tracking, and the UI

`LiveListenerBus` is the observability spine. It is deliberately **asynchronous and
lossy under pressure**:

- Listeners are partitioned into named `AsyncEventQueue`s (`shared`, `appStatus`,
  `executorManagement`, `eventLog`, `streams`). Each queue has its own bounded buffer and
  its own dispatch thread, so a slow listener degrades only its own queue.
- On overflow the queue **drops events** and logs a warning. Any consumer of the listener
  API must therefore tolerate gaps. This is why `AppStatusStore` numbers can drift on
  overloaded drivers.
- `EventLoggingListener` writes the JSON event log consumed by the History Server;
  `ReplayListenerBus` replays it back through the same `AppStatusListener`, so the live UI
  and the history UI are literally the same code over the same `KVStore`
  (`common/kvstore`, LevelDB/RocksDB-backed or in-memory).

`SQLAppStatusListener` in `sql/core/.../execution/ui` does the same for the SQL tab, keyed
by the execution ID that `SQLExecution.withNewExecutionId` stamps into the local
properties of every job in the query.

## 7. Accumulators, Broadcast, and Closure Capture

Three mechanisms move state between driver and executors, and they have very different
guarantees.

**Broadcast** (`core/.../broadcast/TorrentBroadcast.scala`) — the driver chunks the
serialized value into `spark.broadcast.blockSize` pieces stored in its BlockManager.
Executors fetch missing chunks from the driver *or from peers that already have them*,
BitTorrent-style, then republish locally. This is what keeps a 1 GB broadcast join from
melting the driver NIC on a 500-executor cluster. Every task binary is itself broadcast
(see step 6 above), which is why `ContextCleaner` must GC broadcasts aggressively.

**Accumulators** (`core/.../util/AccumulatorV2.scala`) — driver-side merge of executor-side
partial values, shipped back inside `TaskMetrics` on every task completion.
`DAGScheduler.updateAccumulators` merges only from **successful, non-resubmitted** tasks
for named accumulators, giving exactly-once semantics for accumulators used in *actions*;
accumulators updated inside *transformations* can double-count on retry or speculation.
Internal metrics (`InternalAccumulator`) use the same machinery.

**Closure capture** — `ClosureCleaner` (`core/.../util/ClosureCleaner.scala`) rewrites the
captured `$outer` chain of Scala lambdas via ASM so that an anonymous function doesn't drag
its entire enclosing object (and, transitively, the `SparkContext`) into serialization.
This is the mechanism behind the classic "Task not serializable" error, and it is why
capturing a field of an object pulls in the object but capturing a local `val` does not.

## 8. Storage and Caching

`BlockManager` runs on driver and every executor; `BlockManagerMasterEndpoint` on the
driver holds the location index. Blocks are identified by typed `BlockId`s (`RDDBlockId`,
`ShuffleBlockId`, `BroadcastBlockId`, `TaskResultBlockId`, `StreamBlockId`).

- **MemoryStore** holds deserialized blocks (as `DeserializedMemoryEntry`, arrays of
  objects) or serialized ones (`SerializedMemoryEntry`, chunked byte buffers). Unrolling is
  incremental and can fail partway, which is the correct behavior — a cache is a hint.
- **DiskStore** maps blocks to files through `DiskBlockManager`, which hashes block IDs
  across `spark.local.dir` subdirectories to spread I/O across spindles/volumes.
- **BlockInfoManager** implements a **readers-writer lock per block, scoped to a task
  attempt**, with automatic release on task completion. This is what makes concurrent
  `rdd.cache()` from multiple tasks safe.
- Replication (`StorageLevel` with `replication > 1`) uses `BlockReplicationPolicy`, which
  is topology-aware via `TopologyMapper`.

`CacheManager` in `sql/core` sits above this for `Dataset.cache()`, keyed by *canonicalized
logical plan* so that two structurally identical queries share one `InMemoryRelation`.

## 9. Cross-Cutting Concerns

**Security.** `SecurityManager` + `SSLOptions` handle auth secret distribution, RPC
encryption (SASL or AES via `common/network-common`), and local-disk encryption of shuffle
and spill files. In K8s the secret is a mounted secret; in YARN it rides in the
`ApplicationSubmissionContext`. Delegation-token renewal is abstracted behind
`HadoopDelegationTokenManager` and `SupportsDelegationToken`.

**Metrics.** Dropwizard-based `MetricsSystem` with pluggable sources (`DAGSchedulerSource`,
`BlockManagerSource`, `ExecutorSource`, `ShuffleMetricsSource`) and sinks (JMX, Prometheus
servlet, Graphite, CSV).

**Error framework.** Since 3.4 Spark uses **error classes**: a JSON registry
(`common/utils/src/main/resources/error/error-conditions.json`) mapping condition names
like `DIVIDE_BY_ZERO` to SQLSTATEs and parameterized message templates. Exceptions extend
`SparkThrowable`. Tests assert with `checkError(...)` on the condition + parameters rather
than on message strings, which is what makes error messages refactorable. Connect
serializes the condition and parameters over the wire so clients can rebuild typed
exceptions.

**Structured logging.** Log statements use the `log"...${MDC(KEY, value)}..."`
interpolator (`core/.../internal/Logging.scala`, keys in `LogKeys`), emitting JSON with
typed MDC fields. This is visible throughout the DAGScheduler code quoted in the deep dives.

## 10. Design Assessment (Staff+ Lens)

**What has aged extremely well**

- *Lineage over replication.* Cheap to reason about, and the recompute path doubles as the
  speculation and straggler-mitigation path. The cost — indeterminate-stage correctness —
  was patched rather than redesigned, and it works.
- *Coarse-grained executors.* Amortizing JVM startup and enabling cross-stage caching is
  the single biggest reason Spark displaced MapReduce.
- *The Catalyst tree/rule abstraction.* `TreeNode` + `Rule` + `RuleExecutor` is a tiny core
  that has absorbed cost-based optimization, DSv2 pushdown, AQE re-planning, and streaming
  incrementalization without structural change. The tree-pattern bitmask added later
  (§ Catalyst doc) fixed its one real scaling problem — O(rules × nodes) traversal — with a
  backwards-compatible mechanism.
- *AQE.* Deferring physical decisions until real statistics exist is the correct answer to
  the fact that cardinality estimation is unsolvable in general. It is arguably the most
  consequential Spark feature of the last decade.

**Structural tensions**

- *The driver is a monolith and a SPOF.* All scheduling state, all listener state, all
  broadcast origination, and (in Connect) all session state live in one JVM. The
  DAGScheduler's single event-loop thread serializes every scheduling decision in the
  application. At tens of thousands of tasks per second this is a real ceiling, and it is
  why `DAGScheduler.scala` is ~4,900 lines of carefully single-threaded code.
- *Two analyzers.* The fixed-point `Analyzer` and the new single-pass `Resolver`
  (102 files under `analysis/resolver/`) coexist behind `HybridAnalyzer`, with a dual-run
  comparison mode. This is the right migration strategy for a component this
  correctness-critical, but it is a large, long-lived duplication.
- *Shuffle is still the boundary of everything.* Push-based shuffle, the external shuffle
  service, and the pipelined-shuffle work in this tree are all attempts to soften a barrier
  that is fundamental to the stage model.
- *Python interop tax.* Despite Arrow batching, a Python UDF is still a fork/exec'd worker
  with a socket in the middle. The `udf/worker/{proto,core,grpc}` modules in this tree
  suggest a move toward a more formalized, possibly language-agnostic UDF worker protocol.
- *Configuration surface.* `SQLConf` alone carries well over a thousand entries. Most are
  correctly defaulted; the problem is that the ones that matter for a given failure are not
  discoverable from the failure.

**Where the tree is heading (visible from in-flight code)**

1. **Spark Connect as the default client boundary** — the decoupling of `sql/api` from
   Catalyst, reattachable execution, session cloning, and the local server pool all point
   at Connect becoming the normal way to talk to Spark rather than an alternative.
2. **Single-pass analysis** — removing the fixed-point analyzer's unpredictable latency.
3. **Pipelined shuffle** — co-scheduling a consumer stage with a still-running producer
   stage, i.e. partially dissolving the stage barrier for the cases where it is safe.
4. **RocksDB-first state management** in Structured Streaming, with changelog checkpointing
   and offline state repartitioning.

## 11. Reading Guide

If you are new to the codebase, read in this order:

1. `core/.../rdd/RDD.scala` — the five-property model (`partitions`, `dependencies`,
   `compute`, `partitioner`, `preferredLocations`). Everything else is commentary.
2. `core/.../scheduler/DAGScheduler.scala` header comment (lines 55–123) — the best
   architectural document in the repo.
3. `sql/catalyst/.../trees/TreeNode.scala` and `rules/RuleExecutor.scala` — 
   the whole optimizer in two files.
4. `sql/core/.../execution/WholeStageCodegenExec.scala` header (lines ~616–643) — the
   produce/consume protocol.
5. `sql/core/.../execution/adaptive/AdaptiveSparkPlanExec.scala` — how the static plan
   becomes dynamic.
